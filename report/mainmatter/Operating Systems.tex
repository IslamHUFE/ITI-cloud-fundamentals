\chapter{Operating Systems}

\section{Introduction}
The operating system in a computer acts as the intermediary between the hardware and the applications that allow the user to utilize that hardware for meaningful purposes such as playing games, browsing the internet, graphic design, and many other activities.

The operating system is similar to the control unit in a car. A car has an engine, fuel tank, wheels, brakes, and so on. But without the control unit, the car would be nothing more than a collection of mechanical parts connected together.

\subsubsection{Arithmetic and Logic Unit (ALU)}
The ALU carries out \textbf{arithmetic} operations (add, subtract, etc.) and \textbf{logic} operations (AND, OR, NOT, etc.).

\subsubsection{Control Unit (CU)}
Controls the operation of the ALU, memory, and I/O devices, telling them how to respond to the program instructions it reads from memory. It also provides the \textbf{timing and control signals} needed by the other components.

\section{Computer Operating System}

\begin{minipage}[c]{0.6\textwidth}
	\subsection{What is an Operating System?}
	When a computer turns on, the first code to run is the \textbf{bootstrap}, stored in ROM (the BIOS). After booting, many applications and devices need to be handled efficiently, so the user feels the system ``just works''. This is the job of the OS.
	
	\textbf{Definition:} A program that controls the execution of other programs and acts as an intermediate layer between the software and the hardware.
\end{minipage}%

\subsubsection{Main Objectives}
\begin{itemize}
	\item \textbf{Efficiency:} responsiveness and fluidity.
	\item \textbf{Ease of use:} convenient for the user.
	\item \textbf{Abstraction and extensibility:} support for new devices and software.
\end{itemize}

\subsubsection{Main Pieces}
\begin{itemize}
	\item \textbf{Kernel:} the core part that handles low-level functions; it must be running at all times (resident in main memory).
	\item \textbf{Libraries, applications, and tools} shipped with the OS (browsers, frameworks, native apps).
\end{itemize}

\section{Why Do We Need an OS?}
The OS runs and facilitates applications, manages conflicts between them, and provides common services such as security (encryption, authentication, authorization). It abstracts the hardware so applications run seamlessly. The complexities it handles are:

\begin{minipage}[c]{0.6\textwidth}
	\subsection{Complex and Multiprocessor Systems}
	Modern CPUs have multiple cores: \textbf{homogeneous} platforms have identical cores, while \textbf{heterogeneous} ones have cores with different capabilities. Other engines such as the GPU also exist. The OS must schedule programs efficiently across all of them and hide the differences in hardware (display, storage, sensors, etc.) from applications.
\end{minipage}%
\hfill
\begin{minipage}[r]{0.40\textwidth}
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.8\linewidth]{figures/MultiCore}
		\caption{Multi-core CPU}
		\label{MultiCore}
	\end{figure}
\end{minipage}

\subsection{Multitasking}
Many applications run at the same time: \textbf{foreground} applications started by the user and \textbf{background} ones started by the OS. The OS streamlines their execution.

\subsection{Multiuser Systems}
Several users (an administrator and others with different permissions) may use the same system. The OS must give each user fast response while enforcing \textbf{privacy and security} between them.

\begin{minipage}[c]{0.6\textwidth}
	\subsection{Program and Process}
	A \textbf{program} is the static, built code of a solution. When it is triggered to run, the OS assigns it a process ID and tracks it as a \textbf{process}. In short, a process is a \textbf{program in execution}.
\end{minipage}%

\subsubsection{Process Contents}
\begin{itemize}
	\item \textbf{Text section:} program instructions.
	\item \textbf{Data section:} global and static variables.
	\item \textbf{Stack section:} local variables, return addresses, method parameters.
	\item \textbf{Heap section:} dynamic allocation at run-time.
	\item \textbf{Program counter:} address of the next instruction.
\end{itemize}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{minipage}[c]{0.6\textwidth}
	\subsection{Process States}
	A process goes through several states in its lifecycle:
	\begin{itemize}
		\item \textbf{New:} being created.
		\item \textbf{Ready:} waiting to be assigned to a processor.
		\item \textbf{Running:} instructions are being executed.
		\item \textbf{Waiting:} waiting for an event (e.g., I/O).
		\item \textbf{Terminated:} finished execution.
	\end{itemize}
	The OS monitors these transitions and tries to limit switching a process between CPU cores.
\end{minipage}%

	\subsection{Process Control Block (PCB)}
	The data structure the OS keeps for each process:
	\begin{itemize}
		\item \textbf{Process ID} and \textbf{state}.
		\item \textbf{Pointer:} to the parent process.
		\item \textbf{Priority:} used in scheduling.
		\item \textbf{Program counter} and \textbf{CPU registers} (including core affinity).
		\item \textbf{Memory management} information.
		\item \textbf{I/O status:} devices assigned.
		\item \textbf{Accounting:} timers, time remaining, paging needs.
	\end{itemize}

\begin{minipage}[c]{0.6\textwidth}
	\subsection{Context Switching}
	Swapping the running process with another so other applications can run:
	\begin{enumerate}
		\item Pause the current process and \textbf{save its context} (PC, registers, status).
		\item Switch to the new process.
		\item \textbf{Restore} the new process's context.
	\end{enumerate}
	This lets the process continue exactly from where it stopped.
\end{minipage}%

\begin{minipage}[c]{0.6\textwidth}
	\subsection{Scheduling}
	The OS uses queues to organize processes:
	\begin{itemize}
		\item \textbf{Ready queue:} processes ready to be scheduled.
		\item \textbf{Waiting queue:} processes blocked on I/O or a device.
		\item \textbf{Job queue:} all processes in the system (bookkeeping).
	\end{itemize}
	
	\textbf{Scheduling criteria:} CPU utilization, throughput, responsiveness, and resource waiting time, while keeping fairness.
	
	\textbf{Algorithms:} FCFS, SJF, SRTF, Round-Robin, and static/dynamic priority.

\section{Memory Management}
With many processes in memory at once, each needs memory for its \textbf{code}, its \textbf{data} (strings, variables), and \textbf{run-time} requests (stack/heap). The OS and kernel components also need memory, as do some devices (e.g., printer spooling).

\begin{minipage}[c]{0.6\textwidth}
	\subsection{Address Binding}
	A program is loaded into a different memory location each time it runs, and a process swapped out to virtual memory (part of secondary storage) usually returns to another location. So its addresses change at run-time. The solution is to \textbf{map} the program's compiled addresses to actual addresses in physical memory.
\end{minipage}%
\hfill
\begin{minipage}[r]{0.40\textwidth}
	
	\begin{figure}[H]

\begin{minipage}[c]{0.6\textwidth}
	\subsubsection{Logical vs. Physical Address}
	The compiler translates the symbolic addresses in the source code into relative addresses (\textbf{logical addresses}), which are measured from the base address where the OS loads the program. Since physical memory cannot hold all programs, \textbf{virtual memory} is mapped onto it, and the \textbf{Memory Management Unit (MMU)} translates logical addresses into \textbf{physical addresses}.
\end{minipage}%

\section{I/O Management}

\begin{minipage}[c]{0.6\textwidth}
	\subsection{I/O Subsystem}
	Many devices connect to the system (displays, keyboards, storage, sensors, Wi-Fi, Bluetooth), each with its own data format, speed, and error reporting. The OS presents a \textbf{unified I/O system} that hides this complexity from applications.
	
	Peripherals communicate through the data, address, and control buses using protocols such as \textbf{PCIe}, \textbf{I2C}, and \textbf{ACPI}.
	
	A kernel-mode \textbf{device driver} handles all communication with a device and abstracts its details; there is also a \textbf{bus driver} for each bus.

\subsection{Synchronization and Critical Sections}
When one thread changes shared data while another reads it, a \textbf{race condition} occurs and the result is unpredictable. Access to shared variables (shared memory, files, ports) must be synchronized, and the OS provides:

\begin{itemize}
	\item \textbf{Mutex:} enforces mutual exclusion; only the holder of the ``key'' proceeds while the other waits until it finishes.
	\item \textbf{Semaphore:} a generalized mutex; a \textbf{binary semaphore} takes the value 0 or 1 and is used to lock critical sections.
\end{itemize}

\begin{minipage}[c]{0.6\textwidth}
	\subsection{Deadlocks}
	A set of processes become blocked because each holds a resource and waits for another resource held by another process. For example, process A holds resource 1 and needs resource 2, while B holds resource 2 and needs resource 1.
	
	A deadlock can arise only if all four conditions hold:
	\begin{itemize}
		\item \textbf{Mutual exclusion:} a resource is not shareable.
		\item \textbf{Hold and wait:} a process holds one resource while waiting for others.
		\item \textbf{No preemption:} a resource cannot be taken by force.
		\item \textbf{Circular wait:} processes wait for each other in a circle.
	\end{itemize}
\end{minipage}%

\section{File Systems}
Applications read and write files through the OS, which manages them using two components:
\begin{itemize}
	\item \textbf{Directory service:} organizes files in a structured way and controls access (read, write, edit).
	\item \textbf{Storage service:} communicates with the underlying hardware (disks) and abstracts the storage devices.
\end{itemize}

\begin{minipage}[c]{0.6\textwidth}
	\subsection{File Concept}
	A file is a collection of related data stored together and accessed by a unique name. It can be a plain sequence of bytes (\texttt{.bin}), a structured format with headers (\texttt{.exe}), or an application format such as JSON or XML.
	
	Common attributes: location, extension, size, access controls, and operation history. Some are kept in the \textbf{file control block}, which the OS exposes through APIs.
\end{minipage}%
\hfill
\begin{minipage}[r]{0.40\textwidth}

\begin{minipage}[c]{0.6\textwidth}
	\subsection{Directory Name Space}
	Files are organized \textbf{hierarchically} inside folders (directories), and this structure is called the directory namespace. It can be multi-level and supports searching by size, type, access level, etc.

\subsection{Access Control}
Access levels apply to both files and directories. Each user has access IDs and permissions, and each file has its own permissions (read, write, modify). For example, a file can be readable by everyone but writable by no one except its owner. The file system enforces these controls at run-time.

\subsection{Concurrency and Cleanup}
\begin{itemize}
	\item A file in use cannot be moved or deleted by another process; the attempt fails with an error code. Programmers should open files with the proper access level and mode (read/write).
	\item The OS periodically clears unused temporary files (garbage collector), and users can configure automatic cleanup of specific locations.
\end{itemize}

\section{Access and Protection}
Even a single-user, offline system needs protection: programs must be protected from other applications, and critical devices must be guarded. The OS provides APIs for access control and protection.

\begin{minipage}[c]{0.6\textwidth}
	\subsection{User Mode and Kernel Mode (Rings)}
	The OS divides execution privileges into \textbf{rings}, giving programs different access levels.
	\begin{itemize}
		\item \textbf{Ring 3 (user mode):} applications and user services; cannot access the hardware directly.
		\item \textbf{Ring 0 (kernel mode):} the kernel and drivers; highest privilege and direct hardware access.
	\end{itemize}
	In practice, most OSs use only Ring 0 and Ring 3.
\end{minipage}%
\hfill
\begin{minipage}[r]{0.40\textwidth}
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.9\linewidth]{figures/Rings}
		\caption{Protection rings}
		\label{Rings}
	\end{figure}
\end{minipage}

\subsection{Protection}
A threat is any local or remote program that tries to compromise the system's resources. Modern OSs defend with:
\begin{itemize}
	\item \textbf{Authentication:} verifying who the requester is.
	\item \textbf{Authorization:} checking the access level the requester is allowed.
	\item \textbf{Access Control Lists (ACLs):} map resources to permission levels.
	\item \textbf{Encryption} and certificate verification services.
\end{itemize}

\section{Virtualization}

\begin{minipage}[c]{0.6\textwidth}
	Virtualization makes each environment believe it has dedicated access to the hardware. It is delivered through \textbf{Virtual Machines (VMs)}, each with its own \textbf{guest OS} that may differ from the \textbf{host OS}. The \textbf{hypervisor} manages the VMs' access to the hardware, and changes inside a VM do not affect the host or other VMs.
	
	VMs use hardware efficiently and are heavily used in servers and the cloud.
\end{minipage}%
\hfill
\begin{minipage}[r]{0.40\textwidth}
	
	\begin{figure}[H]
		\centering
		\includegraphics[width=0.9\linewidth]{figures/Virtualization}
		\caption{Virtual machines and hypervisor}
		\label{Virtualization}
	\end{figure}
\end{minipage}

\subsubsection{Advantages}
\begin{itemize}
	\item Run operating systems when the physical hardware is unavailable, and run legacy systems.
	\item Easy to create, back up, and migrate machines.
	\item Test software on clean installs, and debug by suspending and resuming a machine.
	\item Emulate more machines than are physically available.
\end{itemize}

\section{User Interface and Shell}

\begin{minipage}[c]{0.6\textwidth}
	The UI is not part of the kernel, but it is considered an integral part of the OS. It can be:
	\begin{itemize}
		\item \textbf{GUI:} a rich graphical interface for interacting with the computer.
		\item \textbf{Shell (CLI):} a simpler text-based command-line interface. Programmers often prefer it for quickly navigating the file system and interacting with the OS.
	\end{itemize}
	The UI and shell can affect a developer's choice of language, command-line arguments handling, and standard input/output pipes.
